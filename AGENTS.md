# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## Commands

```sh
pnpm run check          # Run build, lint, format check, typecheck, tests, and skill freshness check
pnpm run build          # Bundle dist/cli.mjs, copy chrome/design assets, and emit dist/skill-local/SKILL.md
pnpm run build:skill    # Regenerate skills/lavish/SKILL.md from shared CLI guidance
pnpm test               # node:test runner (test/*.test.js)
pnpm run lint           # ESLint over bin src test scripts
pnpm run format:check   # Prettier check
pnpm run typecheck      # tsc --noEmit (checkJs mode)
```

Install with `corepack pnpm install --frozen-lockfile`, never `npm install`. `npm` ignores `pnpm-lock.yaml` and resolves the `^` ranges to newer versions, which makes `format:check` pass locally on formatting the pinned Prettier rejects in CI.

This fork (askzy/lavish-axi) is installed from source, not from npm: `corepack pnpm install --frozen-lockfile && npm run build` in the checkout. `dist/` is gitignored, so the CLI does not exist until `build` runs, and the `lavish-axi` binary is not on `PATH` - it is invoked as `node <repo>/dist/cli.mjs`, which is also what the two generated skills under `dist/` call. The npm package `lavish-axi` is upstream's build; `npx -y lavish-axi` bypasses the fork.

Deliberate divergences from upstream (kunchenguid/lavish-axi), each covered by a guard in `test/fork-customizations.test.js`:

- `share` and `setup hooks` are disabled and reject with `VALIDATION_ERROR`; the ht-ml.app client and the chrome's Publish UI are deleted (see Hosted sharing below).
- Delivered feedback is leased and acknowledged by the CLI after it prints, instead of upstream's `restore` re-queue mode (see Request flow below).
- A reaped or interrupted poll hands the review back to the user instead of re-polling; the generated `/check-lavish` skill drains the queue later (see Local skill install below).
- `lavish-axi prune` runs the store-wide stale-state cleanup on demand (README owns its contract).
- Server replacement is guarded by a build id of the source tree as well as the version, so a checkout that rebuilds restarts the server and an unchanged one does not (see Process model below).

Run a single test file: `node --test test/server.test.js`.
Filter by test name: `node --test --test-name-pattern "createOpenOutput" test/cli-output.test.js`.
Run the opt-in real-browser suites: `LAVISH_AXI_BROWSER_E2E=1 node --test test/layout-audit-browser.test.js test/layout-warning-inbox.browser.test.js` (requires `chrome-devtools-axi`).
Run the opt-in chrome-load guard: `LAVISH_AXI_BROWSER_E2E=1 node --test test/chrome-load-browser.test.js` (~15s; needs any installed Google Chrome or Chromium but _not_ `chrome-devtools-axi` - it drives raw CDP over Node's built-in `WebSocket`, locating the binary itself or taking `LAVISH_AXI_CHROME_BINARY`). Every browser suite skips, never fails, when the flag is unset or the browser is missing.

The `prepack` and `prepare` scripts both run `build` automatically, so publishing always ships a fresh bundle and `git`-based installs (which run `prepare`) get a built `dist/`.
The committed `skills/lavish/SKILL.md` is generated by `pnpm run build:skill`; `pnpm run check` fails if it drifts from the shared no-args home output.
`pnpm run build` additionally emits `dist/skill-local/SKILL.md` (`node scripts/build-skill.js --local`) - see the fork section below. `build` must never regenerate the committed skill, or `check`'s trailing freshness gate becomes vacuous.

- Use TDD for bug fixes and new features (see `test-driven-development` skill).

## Architecture

Lavish Editor is a CLI + local HTTP server that opens agent-generated HTML artifacts in a browser, lets the user annotate elements and selected text ranges, edit Mermaid diagrams as Excalidraw whiteboards, and ships those annotations back to the agent over a long-polling API.

### Process model

The CLI (`bin/lavish-axi.js` -> `src/cli.js`) spawns `lavish-axi server` as a **detached** background process (`src/cli.js:startServer`) and waits for `/health`, which returns `{ ok, app, version }`.
Later CLI invocations reuse the running server only when its health version matches the current CLI version and, for a local build, its `build` id matches the source tree; stale servers are asked to `POST /shutdown`, and a pre-handshake server may be SIGTERM'd only through the PID `lsof` finds listening at its exact address and port whose command is Lavish (`killLavishListener`); other processes can share the port at other addresses, so nothing is ever signalled by port alone, and an unidentifiable listener is reported instead.
Host, port, listener, and link-host resolution lives in `src/paths.js` (`resolveListenHosts`, `resolveConcreteListenHosts`, `resolveLinkHost`, `clientHost`); the default path detects Tailscale (`src/tailscale.js`, `tailscale status --json`, never throws) and gives `serve()` separate concrete loopback and Tailscale listeners, and an explicit `LAVISH_AXI_HOST` disables that automatic path (so `LAVISH_AXI_HOST=127.0.0.1` is the loopback-only opt-out, and every test file sets it so no test shells out to a real `tailscale` binary) but still adds loopback beside the pinned address. Loopback is always requested because it is the one address every CLI probes regardless of its own `LAVISH_AXI_HOST`: agents on one machine run with different settings, and a server pinned to one address alone is invisible to a client with no host, which then spawns a second daemon on the same port and the same `state.json`. Wildcard requests are reduced to loopback before listening, and aliases are DNS-resolved and rejected if any result is an all-interfaces address. A name that does not resolve right now is kept as the name (`keepUnresolved`) on both sides - the server binds and retries it like any failed address and reports it in `network_warning`, and the CLI still requires it - so a DNS failure never silently drops an explicit `LAVISH_AXI_HOST`. `listenOnce` resolves a name through the same lookup and all-interfaces refusal as startup, and `requested_hosts` reports configured names beside the addresses they resolved to. Loopback binds FIRST and is the port's ownership lock: if it is in use by a Lavish server (probed over `/health`, bounded), startup throws before taking any other address, so two servers started concurrently cannot split one port between them. Every concrete address gets the same bounded bind retry, and the "did anything bind yet" check runs AFTER those retries and after the loopback floor - ordering it first made both unreachable whenever the first (or only) host failed. When nothing binds and loopback was not among the requested hosts (explicit `hosts` only), `serve()` binds loopback as a floor. At least one listener must be an address the CLI control channel probes (the primary requested host or loopback), otherwise every listener already bound is closed and startup throws. A requested address that still fails is NOT given up on and never marks the server stale: it stays in `pendingBinds`, is retried in the background for the life of the process (`BIND_RECOVERY_DELAYS_MS`, last delay repeating) and immediately on `/health?reconcile_network=1`, and `applyNetworkState` recomputes the link host, Host allowlist, and phone readiness whenever a listener comes up; the Tailscale address and MagicDNS name enter the allowlist and the link only while the Tailscale listener is bound. Restarting could not free a port another process holds and would drop every live review connection. Every surface that reports network health derives its text from `pendingBinds` (`currentNetworkWarning`), so the warning appears and clears with the bind state and is always logged, not only under `--verbose`. Every mutable the request handlers touch (`idleTimer`, `attachmentSweepTimer`, `bindRecoveryTimer`) is declared before the first listener binds: a reconnecting chrome can attach a live-event socket while later addresses are still retrying, and declaring them after the bind loop was a TDZ `ReferenceError` that crashed restarted servers. `/health` answers 503 until every startup bind attempt has finished; the startup prune (`runStartupPrune`) runs after that, so a slow prune never holds a CLI at 503 past its 5 s wait. `serve()` takes a `detectTailscale` hook (default `detectTailscale` from `src/tailscale.js`; a function returning `{ ipv4, magicDnsName, warning? }` or null, which tests replace with a fake) that `reconcileNetwork` re-runs (cached 1 s) and compares by `tailscaleNetworkKey`, reporting `network_stale` when the identity changes (address, MagicDNS, up/down); Tailscale going up or down while a server runs changes nothing until the next CLI call, which then replaces the server once. The agent-facing skill tells the agent to relay `network_warning` to the user; it never hardcodes a host and relays `session.url` as printed. CLI discovery (`findRunningServer` in `src/cli.js`, host list from `discoveryHosts` in `src/local-address.js`) probes the configured host and loopback in parallel, each bounded, and a response whose `app` is `lavish-axi` wins over a foreign `/health`. Because loopback is the port lock, those two addresses always find a current server. Sweeping every other local interface address is opt-in (`LAVISH_AXI_DISCOVER_ALL_INTERFACES=1`), off by default because it opens a TCP connection to every VPN, tunnel, and LAN address on each CLI invocation, which endpoint monitoring reads as outbound connections. Both health probes (`fetchHealth` in the CLI, `probeLavishHealth` in the server) use `node:http` with the socket destroyed on every exit path, never `fetch`: an aborted fetch leaves its TCP connect running, and an address that drops connections to itself kept every CLI invocation alive ~10s after printing; a connection nobody reads likewise holds the other side's `close()` open. `/health` reports `build`, `state_id` (hash of the state file path), `state_dir`, bound `hosts`, and `requested_hosts`. Installation identity is `isOwnedServer`: a matching `state_id`, or - for a server that reports none - an answer at the CLI's configured host or loopback, where replacing it is the upgrade path; one reached only through the interface sweep without a `state_id` is never adopted or stopped, and another installation's server at a control address is a `SERVER_ERROR` naming its state directory, never used, replaced, or stopped. The CLI adopts the first owned server, retires any other owned server on the port over its own `/shutdown` (never by process name or port-wide signal), and replaces the kept server first when it does not request every address a retired duplicate served (`hostsToServe`), so existing review links survive. It also replaces a server whose `requested_hosts` lack the CLI's explicit host, rechecked once in the startup wait loop when another daemon wins the port, so agents with different hosts converge on one daemon instead of trading it; a server still missing that host after the one retry is a `SERVER_ERROR` naming the address, never a successful open. Every replacement - missing host, upgrade, local build, or changed network - passes everything the replaced servers requested to the new one (`inheritedListenHosts` -> `--also-listen`), so one agent's restart never drops another agent's address and its review links; only an IP that is no longer on a local interface (`localInterfaceAddresses`) is dropped, so a vanished Tailscale address is not retried forever while a still-live one survives a MagicDNS change even when the replacing agent's explicit host disables Tailscale detection. A network-stale replacement happens at most once per invocation; version and build-id replacements do not consume that guard.
README's Network binding, One server per port, and Allowed hosts bullets own the user-facing env vars and the non-loopback security warning.
Two global middlewares run before every route, in this order: a Host-header allowlist, then a mutating-route Origin/Referer guard. The Host allowlist (`buildAllowedHostnames`/`isAllowedRequestHost`) rejects any request whose `Host` is missing or not one this server answers to - the DNS-rebinding defense, since an `Origin`/`Referer` same-origin check alone does not stop rebinding (a rebound page sends its hostile domain in _both_ `Origin` and `Host`, so they still match). The allowlist is loopback names + every concrete listener + the active link host + explicit `LAVISH_AXI_ALLOWED_HOSTS` extras (`src/paths.js:extraAllowedHosts`), minus wildcard binds, and it is a mutable Set that `applyNetworkState` refills as listeners come up; a lone `*` (`allowsAllHosts`) disables the guard. A denied request from a browser (`Accept: text/html`) gets an HTML page naming the working URL (`sendDenied`), as does a missing session (`sendSessionNotFound`); other clients get the JSON error. It is enforced for every bind, not just loopback, so a specific-interface bind stays rebinding-protected while its own hostname works. When a reverse proxy sits in front, `X-Forwarded-Host`'s outermost value is validated against the same allowlist (an AND check, so a spoofed forwarded host only narrows access, never bypasses `Host`). The origin guard then 403s non-GET/HEAD/OPTIONS requests whose Origin (else Referer) is present and does not match this server's origin (`isSameOriginRequest`). Header-less CLI control-channel requests have no Origin and must keep working; the Host allowlist remains their gate. Per-route `isSameOriginRequest` checks stay in place and still reject header-less callers. Behind a reverse proxy the expected origin is built from the outermost `X-Forwarded-Host`'s validated hostname and port plus the outermost `X-Forwarded-Proto`, only after the forwarded authority passes the same allowlist boundary as `Host` (or strict authority validation under the `*` opt-out); `parseHostAuthority` is the one parser both the Host allowlist and the origin check use, so a malformed authority (userinfo, bad port, bare IPv6 literal) is rejected everywhere at once.
The session key is **derived, not secret**: anyone who learns the artifact path (or sees a session URL) knows it, so no route may treat key possession as authorization.
Every `shutdown()` records a log-only `cause` (never widened into the user-facing `reason`, which would let an internal cause render as a banner line that claims something untrue), and default log lines are UTC-timestamped by `formatServerLogLine` (`src/server-log.js`) because `server.log` is append-only across restarts. Detached server stdout/stderr are timestamped inside the server process at real line starts so crash diagnostics in `server.log` stay dated after the parent CLI has already exited; an injected `log` still formats its own lines. The detached spawn uses `bin/lavish-axi-server.js` (published as `dist/server.mjs`, emitted by `scripts/build.js` with `./lavish-axi.js` mapped to the sibling `./cli.mjs`), which installs that writer before dynamically importing the CLI, so a module-load failure is dated too. Each HTTP listener keeps its `error` handler after `listening`, so a post-listen error is logged instead of becoming a fatal unhandled `EventEmitter` error. The detached entrypoint also logs `uncaughtException` through timestamped stderr and exits 1 explicitly; installing that listener without an explicit exit would suppress Node's default termination and leave a potentially corrupted server alive. Ordinary user-facing commands still start through `bin/lavish-axi.js` / `dist/cli.mjs`.
Server self-shutdown keys off live connections (browser live-event WebSockets and agent polls), not session status, so the next `lavish-axi <file>` re-spawns a fresh server and adopts the session from `state.json` when it is still resumable; README's Server cleanup bullet owns the user-facing idle-timeout rules.
Live events travel over a WebSocket at `/events/:key` (upstream #324): the server attaches `handleEventUpgrade` to every listener it binds, including one bound later by background recovery, and each frame is JSON `{ type, data }` with the same event names the former SSE route used (`reload`, `agent-reply`, `agent-presence`, `layout-warnings`, `ended`, `chat-sync`, `chrome-reload`, `chrome-outdated`). WebSocket reads are not CORS-protected, so the upgrade requires a present `Origin` that passes the 3-arg `isSameOriginRequest` plus the Host allowlist, and `isSameOriginRequest` reads `req.headers.*` because an upgrade request is a raw `http.IncomingMessage`. One `events.on(...)` listener per event type fans out through `broadcastLiveEvent`, never one listener per client. A `GET /events/:key` without an upgrade is the legacy SSE route: it answers one `chrome-reload` and closes, so a pre-WebSocket chrome reloads into the current one. The half-open-socket gap (a slept laptop, a dropped VPN path never emits `close`) is closed by the server-side heartbeat (upstream #353): a ping every `LIVE_EVENT_HEARTBEAT_MS` (30 s, `liveEventHeartbeatMs` in tests) and `terminate()` after one unanswered pong, which emits `close` and runs the same cleanup a graceful disconnect does. The chrome reconnects with a 500 ms to 5 s backoff and raises the existing outdated banner ("no longer running") after `LIVE_EVENT_UNREACHABLE_FAILURES` (5) consecutive failures; a successful reconnect retires only a banner that path raised, never one a `chrome-outdated` event raised. `ws` is a runtime dependency because `scripts/build.js` bundles with `packages: "external"`; it is imported dynamically inside `serve()` so `--version` and `poll` never load it.
State lives at `~/.lavish-axi/state.json` (`LAVISH_AXI_STATE_DIR`), shared across all projects and keyed by a sha256 prefix of the canonicalized file path - the canonical HTML path _is_ the identity, so the CLI never needs opaque session IDs (`src/session-store.js:sessionKey`).

### Request flow

1. `lavish-axi <file.html>` (`openCommand`) -> POST `/api/sessions` -> `SessionStore.upsertSession` -> the CLI opens the returned session URL in the browser.
   `--no-gate` sends `noGate`, returns a one-open URL with `?no-gate=1`, and leaves the stored canonical session URL unchanged.
   Sessions record who ended them: `ended_by: "user"` for browser-initiated ends (including the composer's send-and-end, which posts final prompts and the `endSession` flag to `/api/:key/prompts` atomically) and `ended_by: "agent"` for `lavish-axi end <file>`.
   Idle self-shutdown never calls `endSession` - it only stops the server process, leaving session status untouched in `state.json`, so there is no third `ended_by` case to track.
   `/api/sessions` refuses to revive a user-ended session unless the request body sets `reopen: true` (the CLI's `--reopen`), returning `{ status: "user-ended" }` without upserting; agent-initiated ends keep reviving on a plain open.
2. `GET /session/:key` serves a chrome page (`createChromeHtml`) whose sandboxed iframe points at `/artifact/:key/index.html`; the chrome client bootstraps from the `lavish-session` JSON script in the page.
   `extractArtifactHead` (`src/server.js`) adopts the artifact's own `<title>` and `<link rel="icon">` for the chrome tab, but only `data:`, `http(s):`, and protocol-relative icon hrefs - artifact-relative hrefs would not resolve against the chrome page - with fallback to the Lavish defaults.
3. The artifact route runs `injectLavishSdk` (`src/html-transform.js`) to append one `<script src="/sdk.js?key=...">` at the end of `<body>`. Nothing else is injected - artifacts stay byte-identical apart from that tag so they remain portable when opened directly without the server.
4. Sibling assets resolve under `/artifact/:key/<path>`, sandboxed to the artifact's directory both lexically and by **real-path/symlink resolution** - `resolveArtifactAsset` rejects `..` escapes and, in parity with export's `guardedRead`, refuses a path whose symlink-followed real path leaves the directory, so a symlink placed beside the artifact can't make the route serve an outside file; a nonexistent path (`ENOENT`/`ENOTDIR`) falls back to the lexical check for the caller's 404, and every other realpath failure fails closed. It returns the **resolved** path, so `sendFile` re-opening it cannot be redirected by a link swapped in after the check. The packaged Tailwind/DaisyUI assets are still served from `/design/:asset` so older artifacts keep working, but new artifacts are no longer auto-wired to those routes.
5. The injected SDK runs the render-time layout audit and posts each pass - findings plus its own `complete` flag and viewport width - to the chrome. A completed client-side pass releases the visual gate immediately, then the chrome reports it fire-and-forget to `/api/:key/layout-diagnostics`; a failed report must never hold the artifact behind a network round-trip. If a pass loses an artifact-load-token race, the chrome requests a fresh pass (`lavish:requestLayoutDiagnostics`) instead of silently consuming the cycle.
   Detection is **passive**: that route updates the warning inbox and emits a live `layout-warnings` event, and it deliberately never emits `feedback`, so a diagnostic pass can never make `lavish-axi poll` return or wake an agent. The gate reveals on the first completed pass whatever it found (detection and user-facing behavior: README's Layout issues inbox, Layout issue lifecycle, and Open-time layout gate bullets).
   Cosmetic, intentional, transient, tiny, warning-severity, and uncertain observations fail open and never enter the inbox.
   The narrow **fatal** path is separate and still immediate: `/api/:key/artifact-failures` records only `artifact-unavailable` (the chrome's probe of the artifact route failed) or `artifact-asset-unavailable` (the SDK saw a same-origin subresource `error`), marks the session `feedback`, and `takeFeedback` returns them as `artifact_failures`. Ordinary layout findings must never be relabelled fatal to regain auto-repair.
6. User actions in the iframe `postMessage` to the chrome. Queued prompts live in tab `sessionStorage`; unsent prompts sharing the SDK-internal `_lavishQueueKey` replace each other, and that field is stripped before POSTing collected prompts to `/api/:key/prompts`.
   The chrome assigns each queued prompt a unique `prompt_id` at queue time (never trusting an iframe-supplied value), carries it through `queuePrompts` onto the persisted transcript entry, and removes a queued note solely when that transcript acknowledges the same identity - never by displayed content or only by a successful POST response - so a reload after a lost response recognizes an already-accepted note instead of re-sending it. `queuePrompts` filters acknowledged identities (`chat[].prompt_id` plus `chat_ack_ids`) before attachment resolution and layout-warning planning, and reports `fresh_feedback` so an idempotent retry neither conflicts with newer warning state nor wakes an unrelated poll: the route emits `feedback` only when the batch accepted something new. `agentFacingPrompt` strips `prompt_id` before the prompt is stored in `session.prompts`, so it never reaches `takeFeedback`, a lease, or poll output; `delivery_id` (server-minted per batch) and `prompt_id` (chrome-minted per note) are unrelated and no field joins them. Visible `session.chat` is bounded to `MAX_CHAT_STORED_BYTES` (5,242,880) of stored JSON on every state load and transcript append (`applyTranscriptBound` in `queuePrompts`, `addAgentReply`, and `readState`, which persists a bounded legacy transcript before the session is served). Evicted user entries leave their `prompt_id` on `session.chat_ack_ids`, and both the store's ack filter and the chrome's settlement (`initialChatAckIds` / live `ack_ids`) consult that compact list so eviction cannot reopen duplicate send. `chat_revision` lets the chrome accept an authoritative bounded replacement even when no retained entry overlaps its current view, while rejecting stale syncs. `prune`'s unreplied rule reads `chat[].role === "user"`, which includes annotations and whiteboards, so an annotated-only session is not "unreplied".
   The conversation transcript is server-owned display state. Every accepted prompt with text, images, an identity, or an anchor enters `session.chat` through `chatEntryForPrompt` (`src/chat-messages.js`) as a bounded `{ role: "user", kind, text, anchor, attachments, at, prompt_id }` entry - not only composer messages - in the same `queuePrompts` write that appends to `session.prompts`; `takeFeedback`, a lease that expires and redelivers, and the ack never read or write `chat`, so a redelivery never creates a second bubble, and a leased-but-unacked prompt shows as an ordinary sent bubble (delivery is visible only through presence). This is why the fork has no upstream `restore` mode: leases make re-entering `queuePrompts` unnecessary. `/api/:key/prompts` answers with `serializeChatSync(session)` (`{ chat, ack_ids, chat_revision }`) and emits `chat-sync` with the same payload at accept time, so the sending chrome settles its queued bubbles in place and every other tab shows the sent notes before any poll takes the batch; `chat_revision` increments on every transcript change (`queuePrompts` with new entries, `addAgentReply`) and the chrome applies a sync with a higher revision outright, while a sync at the same revision must still carry everything the tab shows. Rendering is computed server-side by `serializeChat`/`renderChatMarkdown` in that module because `chrome-client.js` is served as a raw file and cannot import modules: agent entries ship with their rendered `html` and are the only entries the chrome ever sets as html; user entries ship as text with their anchor and are always escaped; the `agent-reply` live event carries the serialized entry, not bare text. The queued log (`#queuedLog`, the last child of `.panel-scroll`) renders the tab's unsent prompts as the same user bubble in its dashed, removable state, and `promptAnchor` in the chrome deliberately duplicates the server's anchor rule for prompts that have not reached the server yet; `test/chrome-client-queue.test.js` pins the two against the same fixtures so a bubble never changes its anchor when it settles. A note's Sending state is derived from the existing send bookkeeping (the pending snapshot request's prompts and the active submission), never tracked separately, so no failure path can strand a note with its remove control disabled.
   `/api/:key/prompts` is **same-origin guarded** like the reviewer-handoff route: whatever lands there reaches the agent as the reviewer's own instructions, and the key alone must never buy that. Only this server's own chrome may queue prompts, so any test or tool that posts there has to send a matching `Origin`.
   The chrome page (`/session/:key`) also answers `X-Frame-Options: DENY` and `frame-ancestors 'none'`, denying an attacker page both a window handle to the chrome and a clickjacking surface over Send. The header is scoped to that route on purpose - `/artifact/*` is framed by the chrome.
   The route rejects every new batch for an already-ended session (409 `status: "ended"`), including a redundant send-and-end batch, because no later poll will deliver it.
   Text selection prompts use `tag: "text"` with a `target` of `type: "text-range"` (selected text, `commonAncestorSelector`, start/end boundary anchors).
   Mermaid diagram-node prompts for rendered SVGs outside `.mermaid` containers use `tag: "mermaid-node"` with a `target` carrying `diagramId`, `nodeId`, the rendered `label`, and a `selector`, so the annotation anchors to node identity and survives a re-render that reshuffles the SVG.
   Composer and annotation-card keyboard conventions, button layout, and the conversation panel are user-facing behavior owned by README's Feedback controls and Keyboard shortcuts bullets.
7. `lavish-axi poll <file.html>` (`pollCommand`) hits `GET /api/poll`, or `POST /api/poll` when it atomically publishes an `--agent-reply` or takes over before waiting.
   Poll ownership is exclusive per session and lives only in the server's `activePolls` map (session key -> holder `{ key, owner, startedAt, replaced, replace }`), never in `state.json`. A second poll receives 409 typed `LISTENER_ACTIVE` with the holder label (`--owner <label>`, else `agent-listener`) and age; `--takeover` installs its holder before releasing the old poll with typed `LISTENER_REPLACED`, so the displaced poll's cleanup (`releasePollListener`, which only drops the holder that still owns the key) cannot erase the successor. Claims serialize through `pollOwnershipLock`, including the reply write, so a refused poll never publishes its reply. The map also supplies the `listeners: [{ key, label }]` that `/health` exposes for the home listing's `listener` column. Poll GETs and POSTs reject a present foreign Origin or Referer while header-less CLI access keeps working.
   A zero-timeout drain (`--timeout-ms 0`, the `/check-lavish` hand-back path) is not a listener: `handlePoll` reads `timeoutMs` before the ownership block and a drain claims nothing, emits no listening presence, is never refused with `LISTENER_ACTIVE`, and rejects `--takeover` (400) because there is no wait to take over. It still takes, leases, and marks delivery like any other take, and `--agent-reply` on a drain still publishes.
   Upstream's `restoreClosedFeedback` (re-queueing a batch through a `restore` mode) is replaced by `store.releaseFeedback(key, delivery_id)`: when the poll that took a batch was displaced or its client had gone, the server expires that lease now (`leased_at` set to the epoch) and emits `feedback`, so the successor or any waiting poll takes it at once instead of after `FEEDBACK_LEASE_TTL_MS`. `--takeover` never touches a lease otherwise; only `--takeover --agent-reply` retires leases, through the same `addAgentReply` rule every reply follows.
   Every take that leases a batch emits a `lease` event carrying the TTL, and a waiting poll's `onLease` arms its lease timer for it (`armLeaseTimer` keeps the soonest deadline). Without that, a drain that leased a batch while a poll waited created a lease the waiting poll never timed, and an unacked drain left the batch sitting until some other event woke the listener. A lease timer that fires to find the lease acked re-arms and keeps the poll waiting rather than cleaning it up.
   Queued prompts or fatal artifact failures - including prompts queued before an ended session - are returned immediately and mark the session as observed by an agent; otherwise the poll marks the session actively listening and long-polls on an `EventEmitter` until a `feedback`, `ended`, `lease`, or `browser-disconnected` event fires.
   Delivery is a lease, not a delete: `takeFeedback` moves the batch into `session.leases` under a `delivery_id`, the CLI acks it (`POST /api/:key/ack`) only after the output has drained to stdout, and `--agent-reply` retires every lease on the session. A lease unacked for `FEEDBACK_LEASE_TTL_MS` (about a minute) is delivered again on the next poll, including `--timeout-ms 0`, and a waiting long-poll wakes for it; a waiting response carries `retry_after_ms` while a lease is outstanding. `writeState` writes a temp file and renames it over `state.json`, so a crash mid-write cannot truncate the store.
   A user-queued layout-issue batch arrives here as an ordinary `tag: "layout-warnings"` prompt with a `type: "layout-warnings"` target - indistinguishable from other feedback at the CLI boundary, which is what lets a nonblocking relay consume it without special handling. `layout_warnings` is no longer a poll field.
   A `status: "ended"` response carries `ended_by`; the final `status: "feedback"` batch delivered right before a session ends carries the same signal via `session_ended: true` plus `ended_by`, so that last `next_step` also skips the reopen instruction.
   Default no-timeout polls stream whitespace heartbeat bytes before the final JSON response; `--timeout-ms` is a non-streaming test/debug escape hatch.
   Key order in `createPollOutput`'s feedback object is a contract, not incidental: `prompts`, `artifact_failures`, then `next_step` all come before the unbounded `dom_snapshot`, so an agent that truncates or filters the response still reaches the user's own words and the instruction that continues the review loop (`test/cli-output.test.js` guards the emitted order). Never move `next_step` after the snapshot: it is the only field carrying the reply-and-poll-again directive, the attachment paths, and the session-ended "stop polling" rule.
   Losing the last `/events/:key` WebSocket client for a session while a poll is active starts a per-session reconnect grace timer (`BROWSER_DISCONNECT_GRACE_MS`) from the `cleanup` that `attachLiveEventClient` returns, whether the socket closed gracefully or the heartbeat terminated it; a reconnect cancels it, while expiry releases the poll with the non-terminal `browser_disconnected` and leaves the stored session open. The disconnect result replaces only a `waiting` take, so it never consumes or retires a lease, and a `--timeout-ms 0` drain is unaffected. Poll cleanup cancels the timer once no poll is active, so a timeout, feedback, or explicit end cannot leave a stale disconnect for a later poll.
   The CLI always writes the one-shot wait banner to stderr for no-timeout polls - it is the "not hung" signal an agent needs while stdout stays empty - but writes the recurring per-minute wait ticks only when stderr is an interactive terminal (`shouldNarratePollWaitTicks`), so agent harnesses with piped, non-TTY stdio get no unbounded tick noise in their merged capture. Stdout stays reserved for the final JSON/TOON response.
   If SIGINT or SIGTERM interrupts a no-timeout poll, the CLI writes re-run guidance to stderr and exits with the conventional signal code; queued feedback persists, so re-running the same poll is safe.
8. The `/events/:key` WebSocket emits server-derived `agent-presence` data. Its `state` is `waiting` before any poll has attached, `listening` while one is active, and `working` after a poll has delivered feedback; `computePresence` ranks working above listening, so a poll attaching while a delivered batch is unanswered keeps showing working. Its `mode` (omitted while `waiting-on-captain`) distinguishes `agent-listener`, an owner-labelled `external-listener`, and `agent-busy`; the chrome maps `external-listener` to its `external` state ("External listener active") so a supervisor-owned listener never looks like an idle turn for the user. The chrome allows queued feedback while waiting, listening, or external and blocks sends only while working.
   An agent reply (`publishAgentReply`, reached from `POST /api/:key/agent-reply` and from `POST /api/poll` with `agent_reply`, which is how the CLI's `--agent-reply` and `--agent-reply-file` arrive) concludes the working state and returns presence to `waiting`, so sends re-enable as soon as the agent answers instead of staying blocked until another poll attaches. A batch delivered with `session_ended` clears delivery right after the holder is released, because no later poll or reply can. A successful ownership claim retires the previous round's delivery marker; releasing a poll never does. Presence changes are compared as state plus mode (`presenceSignature`), so a takeover between a bare and an owner-labelled listener is visible even though both states are `listening`.
   Every poll exit path has to undo the presence it set: `handlePoll` subscribes to request and response closure before its first `await`, re-checks closure and replacement after each destructive take, and reconciles a browser disconnect that fired before its handlers were armed (`browserDisconnectPending`), so an abandoned or displaced poll cannot strand ownership, presence, or a leased batch. A reaped poll releases its listener from the socket `close`, which is why a stuck `LISTENER_ACTIVE` always means a poll process that is still alive.
   An `ended` live event makes every connected chrome read-only immediately. The socket is registered in `liveEventClients` before `sendInitialLiveEventState` reads session state, then sends an `ended` snapshot when that state is already terminal; the bootstrapped `initialEnded` state covers pages loaded after the end, and `markSessionEnded()` is idempotent across redundant signals.
   `--agent-reply` and `--agent-reply-file` post a chat message into the session before polling, rendered in the browser conversation panel via the same stream; README's CLI reference owns when to use each input. `lavish-axi reply` (`replyCommand`) posts that same message to `POST /api/:key/agent-reply` and exits 0 only after the route answers `sent`; the whole receipt request (connect, headers, body) shares one deadline, `AGENT_REPLY_RECEIPT_TIMEOUT_MS`, and a timeout exits non-zero telling the agent to check the conversation before re-posting. It must not claim a poll: a poll stays open until feedback arrives, so it cannot be the acceptance receipt, and it never touches `activePolls`, so it is safe while another poll holds the session. `addAgentReply` is the one place a reply retires leases, so every input - both poll flags and `reply` - retires them. With `requireOpen` (the `/agent-reply` route) an ended session returns before that lease clear and the route answers 409 `{ status: "ended", ended_by }`, so a refused reply leaves the final `session_ended` batch leased and the next `--timeout-ms 0` drain still delivers it; `POST /api/poll` with `agent_reply` keeps posting on an ended session because that drain is how the final batch is collected.

### Passive layout-warning inbox

`src/layout-warnings.js` is the whole lifecycle, as pure functions over stored records, so it is unit-testable without a browser or a server; `SessionStore` and the routes only persist and serve what it returns.
Identity is `layoutWarningFingerprint` over rule + normalized target + viewport class - **magnitude is deliberately excluded**, so a finding that worsens updates one record instead of inflating the count.
Every observation is stamped with an **artifact revision**: `session.artifact_revision`, incremented by the server-owned `beginArtifactLoad` epoch before navigation. The artifact document route only verifies the current load and serves it. Every transition that needs "a newer successful artifact load" (resolved, recurring, dismissal expiry) keys off the revision.
The reviewer handoff is a server-issued single-reviewer capability. Begin requests return typed `superseded`, `no-handoff`, or `out-of-order` outcomes; the chrome may re-handshake once for `no-handoff`, but only an explicit takeover reload can replace a superseded reviewer.
The active load is **durable**, not process state: `beginArtifactLoad` writes the whole epoch - token, revision, pass fence, and the `request_id`/`request_sequence`/`handoff_token` a later begin is judged against - to `session.artifact_load`, and `SessionStore` restores it (and the handoff that owns it) the first time a process asks for it, because the `upgrade` restart replaces the server under reviewers who did not ask for it. Only a newer `beginArtifactLoad` retires a load - not a restart, and not reopening the session. A stored load the restore cannot read as a whole is treated as none, which degrades to one re-handshake and a fresh epoch. The restart tests in `test/session-store.test.js` and `test/server.test.js` pin all three.
`applyDiagnosticPass` is conservative by construction and each guard is load-bearing: a pass for one viewport class returns other classes untouched; an incomplete pass marks active warnings `unverified` instead of clearing them; absence at a revision the warning was already seen on is not resolution; and re-observing an identical finding on the same revision returns the record unchanged so repeat passes do not rewrite `state.json`.
`queued` is a request, not a fix - it stays in the active count and only `recurring` (a newer revision still found it) makes a warning selectable again.
Display strings are computed server-side (`serializeLayoutWarnings`) because `src/chrome-client.js` is served as a raw file and cannot import modules; the chrome renders what it is given and never decides that a warning went away.
The chrome bootstraps the inbox from `initialLayoutWarnings` in the session JSON and re-syncs over the live-event socket, so the inbox survives a browser refresh or reconnect; only per-chrome drawer selection lives in `sessionStorage`, keyed per session so it cannot leak across artifacts.

### Image attachments (server side)

Image attachments (`src/attachment-store.js`) are content-addressed: the id is `<sha256-of-bytes>.<ext>` and the file under `<state-dir>/attachments/<sessionKey>/` _is_ the identity, so the client never dictates a path or id. The chrome performs the same-origin `POST /api/:key/attachments` (raw body, magic-byte validated - a lying Content-Type is ignored; only PNG, JPEG, WebP), `GET /api/:key/attachments/:id` serves the bytes, and `DELETE` is reference-counted. Upload and delete reject header-less and foreign-origin callers like `/prompts` does, with the same 3-arg `isSameOriginRequest(req, allowedHostnames, allowAnyHostname)` so a reverse proxy's `X-Forwarded-Host` works.
The upload route reads the request stream itself via `readAttachmentUploadBody` rather than `express.raw({ limit })`: raw-body aborts on a too-large `Content-Length` WITHOUT draining, which leaves the browser's in-flight upload reset mid-stream instead of receiving the 413. The manual reader buffers up to the cap but always drains to end-of-body, then the route sends a clean 413. The body-parser middleware skips this one route for the same reason. Do not reintroduce a body-parser `limit` on it.
The **trust boundary** is `SessionStore.queuePrompts`: a queued prompt carries only the client's `id` + display `name`; `resolvePromptAttachments` re-derives every authoritative field (absolute `path`, mime, bytes, dimensions) from disk via the injected resolver, so a crafted `/prompts` POST cannot aim an attachment at an arbitrary file. Resolution is **all-or-nothing**: a malformed field/entry, any unknown id, or a count/byte-cap breach rejects the whole batch (`{ rejected, caps }`, persist nothing, 400), never a silent partial-drop. `boundAttachmentRefs` runs BEFORE the resolver: the in-resolver cap counts RESOLVED refs, so thousands of well-formed ids for missing files would each buy a sequential `stat` under the store's single mutex; raw per-prompt and request-wide (`MAX_REQUEST_ATTACHMENT_REFS`) counts are rejected up front and the reported rejection list is capped (`MAX_REPORTED_ATTACHMENT_REJECTIONS`). New pre-resolve validation belongs in that same pure gate - never after the first `await` into the filesystem.
The server routes its attachment disk sections (upload finalize, delete, the sweep) through `store.runExclusive` so they share the store's lock, keeping the reference snapshot + delete atomic against `queuePrompts`. `referencedAttachmentIds` is a pure read and must stay lock-free - the server calls it from inside `runExclusive`, so self-locking would deadlock.
The reference set has three tiers in this fork, because delivered batches are leased (see Agent presence in README): ids on a pending prompt, ids on any lease (live or expired - an expired lease is redelivered with the same resolved paths, so `takeFeedback` never re-resolves), and ids delivered within `ATTACHMENT_DELIVERY_GRACE_MS` (`delivered_attachments`, written by `takeFeedback`, carried across `upsertSession`, capped at `MAX_DELIVERED_ATTACHMENTS`). The grace covers the agent that just acked or replied and is still opening the paths it received; it is a bounded read window, not a second lifetime. `prune` removes a pruned session's whole attachment dir, since nothing can reference it once the record is gone.
Cleanup (`sweepAttachments`, run at server startup + hourly) is **reference-aware**: a file is reaped only when it is both past its TTL AND unreferenced, and the disk cap only ever evicts unreferenced files older than `ATTACHMENT_EVICTION_GRACE_MS` (a just-uploaded image may sit in an open card that has not queued yet). The cap charges **allocated** cost (`chargedBytes`: whole `ATTACHMENT_ALLOC_BLOCK_BYTES` blocks plus the `.meta` sidecar's block), not logical image bytes, so a flood of tiny magic-prefix uploads cannot sit under it. `admitAttachmentCharge` inside `writeAttachment` is the single **upload-admission chokepoint**: it reclaims toward `cap - newCharge`, measures the true committed allocation, and refuses with **507** when the write would not fit. Dimensions are persisted at upload in a `<id>.meta` sidecar so `resolveAttachment` (every `/prompts`) and the GET never re-read the whole image. Files and dirs are created owner-only (`0600`/`0700`). Env limits floor BEFORE the bounds check and require `>= 1`; only `0`/`off` may disable one. User-facing limits and env vars are owned by README's Image attachments bullet.
The chrome and SDK side of attachments (upload mediation, pills, composer chips) is not ported yet; `createChromeHtml` already emits `attachmentMaxBytes`/`attachmentMaxCount`/`attachmentAcceptedMime` and `createSdkJs` already passes `key` and `{ maxAttachmentCount, maxAttachmentBytes, acceptedImageMime }` to `createArtifactSdk` for it.

### Live reload

While a session has a queued (not yet re-checked) layout-warning batch, the reload debounce widens to `BATCH_RELOAD_DEBOUNCE_MS` so an agent's related saves coalesce into one artifact refresh for that group.
`chokidar` watches the artifact file itself by default - watching the entire parent directory recursively saturated the event loop when artifacts lived inside large trees like `~`.
The opt-in attribute/meta (user-facing contract: README's Live reload bullet) switches the watcher to the artifact's directory, excluding `.git`, `node_modules`, `dist`, `build`, `.lavish-axi`.
Any file change emits a `reload` live event and the chrome reloads the iframe; the SDK reports scroll position with `lavish:scroll` and the chrome replays it with `lavish:restoreScroll` after the iframe loads, because the sandbox prevents direct scroll reads.
The same channel preserves the rest of the in-iframe review context: `lavish:reviewState` carries an open annotation card's unsent text and the values of controls inside a `data-lavish-question` scope, and `lavish:restoreReviewState` replays them after the load. Restoration sets values directly and dispatches **no** synthetic `change`/`input` events, because the artifact's own handlers queue prompts and replaying them would silently re-queue answers. Application-owned form state outside `data-lavish-question` is deliberately left alone.
That reported state is also **persisted** per session (`lavish-axi:review-state:<key>` in `sessionStorage`, beside the queue's own key) and restored on boot, because it is the user's own writing and the chrome's in-memory copy dies with the document: an iframe live-reload replayed it, but a full page reload destroyed it. The SDK reports `card: null` when a card is queued or cancelled, which is what retires the stored draft, so a stale draft can never reappear over a later card.
During version-driven shutdown, the server sends `chrome-reload` to the live-event clients of the ONE session named by `POST /shutdown`'s `reload_key` - the session `lavish-axi <file>` is about to open - and `chrome-outdated` to every other connected chrome; a shutdown that names no key (`lavish-axi stop`, idle self-shutdown) reloads nothing. `chrome-outdated` shows a dismissible banner in the conversation panel and never reloads by itself: a forced reload of a page the user is reading or writing in is the behavior this replaced. For the same reason `reloadChromeAfterServerRestart` shows that banner instead of reloading whenever an unsent annotation draft exists.
The banner's line is chosen by the shutdown's own `reason` (`SHUTDOWN_REASONS`: `upgrade` and `local-build` from `ensureServer`, chosen by `serverReplacementReason` from whichever branch of the fork's build-aware `shouldRestartServer` fired, and `stop` from `lavish-axi stop`), and every branch must be true where it is shown. An unrecognized or absent reason is dropped at the route and renders the line that claims neither. Every recovery control probes `/health` (bounded by `HEALTH_PROBE_TIMEOUT_MS`, three outcomes: running, not running, no answer) before navigating, because a reload into a dead port replaces a recoverable page with the browser's own connection-error page, which no Lavish code can undo.
`reloadChromeAfterServerRestart` waits up to `CHROME_RESTART_WAIT_MS` for a healthy `/health` answer and never reloads on a deadline alone; a wait that ends on the deadline re-probes before deciding. When the server never comes back it raises the "Lavish is not running." card with `setLayoutGateFailure(..., { sticky: true })`: a later successful load or diagnostic pass clears the ordinary artifact-load failure card but never this copy, because nothing else tells the user the page is running the pre-upgrade client. Sticky governs copy only: a completed pass, the `layoutGateBypass` **Show anyway** button, or the gate timeout still reveal the artifact underneath. A sticky card also refuses to be overwritten by a non-sticky failure.
A draft is retired only on a definite answer: the SDK re-queries the anchor after `REVIEW_DRAFT_ANCHOR_SETTLE_MS` before reporting `lavish:reviewDraftUnrestorable` (the load event says the document parsed, not that script-built or Mermaid content rendered), and the chrome retires the stored draft only when a SECOND artifact revision reports that same selector missing. The retired text is handed back verbatim as an `Unsent annotation` note in the conversation panel, persisted per session (`lavish-axi:retired-drafts:<key>`), and no handed-back note is ever dropped to make room for a newer one.
Hand-edited files in `dist/` won't trigger reloads.
Run `lavish-axi server --verbose` (or set `LAVISH_AXI_DEBUG=1`) to log session and watcher events to stderr when diagnosing wedges; detached server stdout/stderr is also appended to `server.log` in `LAVISH_AXI_STATE_DIR` for startup and crash diagnostics.

### Export (local-asset inlining)

`src/export-bundle.js` (`buildSelfContainedHtml`) inlines only an artifact's **local** assets: local stylesheets/classic scripts become inline `<style>`/`<script>`, and local images/fonts/icons, confined fetchable `file://` refs, and CSS `url(...)`/`@import` become data URIs (recursively, resolved relative to each stylesheet).
Remote references are deliberately left as links; the user-facing contract, including the size-cap env vars and their defaults, lives in README's Export bullet.
The transform makes **no outbound requests** (no fetching, no SSRF); its only security surface is local file reading, which is confined to the artifact directory both lexically (`confineDir`) and by **real-path/symlink resolution** in the default `readLocalFile` (`guardedRead`), so a symlink inside the directory can't exfiltrate an outside file (e.g. `~/.ssh/id_rsa`) into a shared bundle.
Absolute `file://` paths in non-inlined regions are redacted to `about:blank` so local paths do not leak into an export the user passes around; the injected Lavish SDK is stripped; in-document fragment refs (`#a`, encoded `%23a`) are left alone; and inlined `</script>`/`</style>` are escaped so they can't break out.
The transform records `warnings` rather than failing, split into unresolved local assets (such as `load-failed`, `outside-root`, `too-large`, or unsupported local references left external) and notices (such as `csp-meta` or `file-url-redacted`).
It is dependency-injectable (`readLocalFile`, `resolveAbsolute`, `confineDir`, size caps) so it is testable without disk; the server passes `resolveAbsolute: resolveDesignAssetPath` to inline legacy `/design/*` references from the packaged assets.
The chrome's **Export standalone HTML** overflow-menu item `GET`s `/api/:key/export`; the CLI exposes the same transform as `lavish-axi export`, server-independently.
Lavish's own `Content-Security-Policy` headers are the artifact routes' `ARTIFACT_CONTENT_SECURITY_POLICY` and the chrome page's `frame-ancestors 'none'`; neither constrains artifact content (the sandboxed iframe relies on the `sandbox` attribute, not CSP). Author-set CSP meta tags are preserved and reported as export notices because they may still block exported inline assets.

### Hosted sharing (ht-ml.app) - removed in this fork

Upstream publishes the local-inlined HTML to ht-ml.app, a third-party host that is not part of Lavish. **This fork does not publish anywhere, and there is no longer any code here that could.**

Deleted outright: `src/html-app.js` (the ht-ml.app HTTP client), `createShareOutput` in `src/cli.js`, the chrome's **Publish link** overflow-menu item and share dialog markup in `src/server.js`, the `openShareDialog`/`closeShareDialog`/`publishShare` handlers and their listener wiring in `src/chrome-client.js`, and the `.share-*` rules in `src/chrome.css`. Do not restore any of it when replaying upstream.

Kept, deliberately, as rejections rather than deletions - a rejection tells an agent the feature is _deliberately gone_, where a 404 or "unknown command" reads as a broken build:

- `lavish-axi share` throws `AxiError` / `VALIDATION_ERROR`, pointing at `lavish-axi export`.
- `lavish-axi setup hooks` throws the same way.
- `POST /api/:key/share` answers **410** unconditionally.

Two traps when merging upstream here:

- **The chrome bar template line is a crash surface.** `src/chrome-client.js` resolves chrome elements into top-level `const`s and assigns handlers at module scope, so a restored `document.getElementById("shareArtifact")` reference without the matching button throws during initialisation and kills the **entire** chrome script - annotation, the feedback loop, everything. Markup and client code must move together. `test/fork-customizations.test.js` asserts absence across the rendered chrome, `chrome-client.js`, and `chrome.css` for exactly this reason, and `test/chrome-load-browser.test.js` catches the general case in a real browser (see Things to know when editing).
- **`isSameOriginRequest` / `normalizeOrigin` in `src/server.js` are NOT dead.** Upstream added them for the publish route, but `POST /api/:key/chrome-loads/begin` (#210) needs the same CSRF guard. A previous sync wave deleted them as dead code and the next wave had to restore them. Leave them alone.

### Local skill install (`dist/skill-local/`) - fork only

`~/.claude/skills/lavish` is a symlink at `dist/skill-local/`, so the file an agent session loads is generated, not copied. It was a hand-adapted copy for a while and went a month stale; regenerating it on every build is what makes that impossible.

The only difference from the committed skill is the invocation: `createSkillMarkdown({ invocation })` renders `node <repo>/dist/cli.mjs ...` plus a two-sentence fork note. `npx -y lavish-axi` in this flavor would fetch upstream's package from npm and bypass the fork entirely - sharing re-enabled, no guards - with nothing about the session looking wrong, which is what `test/skill-local.test.js` guards. `scripts/build-skill.js` derives the absolute path from its own location: never hardcode a checkout path in source, and keep the output under gitignored `dist/`.

Node realpaths that location, which on this machine means a 130-character path through `Library/CloudStorage`, repeated 17 times in a file every session loads (about 700 characters of context). `shortestEquivalentPath` trades it for the shortest candidate whose `realpath` matches the derived root - the shell's unresolved `PWD` when the build is run from the checkout - and falls back to the realpath when none qualifies. Any candidate added there must be `realpath`-verified, never string-guessed: an unverified shortcut points every agent at a path that may not exist, which is strictly worse than a long path that works.

### AXI integration

The CLI is built on `axi-sdk-js` (`runAxiCli`).
The `home()` callback returns the rich object shown when the user runs `lavish-axi` with no arguments - the same TOON-serialized output that lands in the agent's optional `SessionStart` hook (upstream writes that hook with `lavish-axi setup hooks`, which this fork disables, so the hook is added by hand); top-level `--help` returns the same static guidance without dynamic sessions.
Poll execution guidance is shared across home output, help, `next_step` responses, and the generated skill through `POLL_WAKE_PATH_RULES`, so every surface states one completion-aware wake-path contract. This fork keeps upstream's requirement that a poll's wake path be observable but drops its foreground-by-default mandate: harnesses here cap foreground command duration, so a tracked background poll is a supported path, and the remaining rules (a completion-aware facility, no fire-and-forget, no "monitoring" claim before the wake path is live) are what keep it from becoming a dead feedback loop.

Agent-facing design guidance is single-sourced in `src/design-reference.js`: `DESIGN_PRIORITY_RULE` states the design-direction priority order exactly once, and `DESIGN_SYSTEM_HINT`, the `lavish-axi design` summary, and the design command help all embed it - never restate the rule on another surface (README carries only a one-sentence summary).
`src/skill.js` renders the installable Agent Skill from the same home output, rewriting command examples to a single parameterised invocation (`npx -y lavish-axi ...` by default) and omitting live session state.
The generated skill intentionally omits a `version` frontmatter field because release-please updates `package.json` without regenerating `skills/lavish/SKILL.md`.
`skills/lavish/SKILL.md` is the only public Agent Skill upstream ships through npm; this fork's installable skills are the generated `dist/skill-local/` and `dist/skill-local-check-lavish/`.
The repository-local `.agents/skills/lavish-design/SKILL.md` brand skill is internal and must keep `metadata.internal: true` so `npx skills add ... --list` and skills.sh hide it unless `INSTALL_INTERNAL_SKILLS=1` is set.
The bare-arg form (`lavish-axi some.html`) is normalized into `["open", "some.html"]` by `normalizeArgv`, which must let the SDK's `RESERVED_COMMANDS` (such as the built-in `update` self-updater) pass through untouched; otherwise the bare-arg rewrite turns `lavish-axi update` into `["open", "update"]` and the inherited reserved command never reaches `runAxiCli`.
This fork shadows that built-in with `updateCommand`: `isFromSourceInstall` treats a package root with a `.git` entry (directory or worktree file) or one outside any `node_modules` as a checkout, and the command then throws `VALIDATION_ERROR` carrying `FROM_SOURCE_UPDATE_RECIPE` before any registry lookup; a real global install is passed to the SDK's `runUpdate` unchanged. Shadowing also removes the SDK's appended built-in help, so `createCommandHelp` carries the `update` entry.

### Whiteboard (Mermaid to Excalidraw)

At view time the SDK replaces each rendered Mermaid diagram inside a `.mermaid` container with an inline whiteboard: a sibling sandboxed iframe (`allow-scripts allow-popups`, no `allow-same-origin`, `data-lavish-ui`) hosting `/whiteboard-frame`, while the hidden container keeps the Mermaid source authoritative - standalone and exported artifacts render plain Mermaid because the SDK is absent.
Inline frames boot locked in view mode behind a click-catcher so embedded canvases never trap page scrolling; a click unlocks editing, and a Fullscreen action reopens the same diagram in the chrome's overlay (the inline frame parks on `about:blank` meanwhile so two editors never autosave one sidecar).
The frame bundle (`src/whiteboard-frame.js`, built by `scripts/build.js` into `dist/whiteboard/` with Excalidraw, the converter, React, and vendored fonts) converts the diagram with `@excalidraw/mermaid-to-excalidraw` and mounts the editor; flowchart, sequence, class, ER, and state diagrams become editable shapes with Mermaid node/edge ids preserved (`regenerateIds: false`), and every other diagram type becomes an image the user draws on (`imageFallback`).
Frames have no server access: each frame gets a signed, short-lived channel token in its HTML, reports directly to `window.top`, and accepts commands only from that top window; the chrome verifies the token at `POST /api/:key/whiteboard-channel`, binds the frame window and token to its diagram index, then fetches sources (`GET /api/:key/mermaid-sources`, extracted from the artifact file on disk by `src/mermaid-source.js` in `.mermaid` document order) and saved scenes, passes them back over postMessage, and performs all writes.
That channel token is **not** a secret and must never be treated as one: `/whiteboard-frame` has to stay framable by any origin - its legitimate parent is the artifact iframe, whose sandbox gives it an opaque origin that no `frame-ancestors` expression can name - and the frame hands its token to whatever window frames it. Two independent guards carry the trust instead, and both are load-bearing.
Binding: the token is signed over the **session key** (`createWhiteboardChannelToken`/`isValidWhiteboardChannelToken`), so it is a capability for one session only, and `/whiteboard-frame` therefore requires `?key=` and 400s without it; signing `${now}.${nonce}` alone let a token minted with no session named at all authenticate any session.
Descent: the chrome accepts inline whiteboard messages **only from windows whose `parent` is the current artifact frame** (`isArtifactChildWindow` in `src/chrome-client.js`) - descent, not token possession, is what proves the sender is ours; without it, any window that can `postMessage` to the chrome (a popup opener, or a page that framed it) could open a channel and queue a fabricated prompt as the reviewer.
Scenes autosave (debounced) through `PUT /api/:key/whiteboard/:index` into per-diagram sidecar files under `<state-dir>/whiteboards/<key>/` (`src/whiteboard-store.js`) - never into `state.json`, which is rewritten wholesale on every store operation; an authenticated `lavish-whiteboard:flush` performs a bounded save before version-driven chrome reloads.
Whiteboard write routes are same-origin guarded and get a 20 MB JSON limit (`isWhiteboardWriteApiPath`); everything else keeps the 2 MB default.
Staleness is hash-based (`mermaidSourceHash`): a live reload that changes the diagram shows a banner in an open whiteboard. Reopening prompts re-convert vs keep-editing only when the saved scene has preservable edits versus its conversion baseline (`resolveWhiteboardInitAction` in `src/whiteboard-core.js`); an unmodified autosave-on-view silently re-converts. Stale user edits are never silently merged.
"Queue feedback" exports the scene and a PNG server-side (`POST .../feedback-files`), then queues a normal prompt with `tag: "whiteboard"` and an `excalidraw-scene` target carrying a bounded edit summary (diffed from the conversion baseline by `summarizeSceneEdits` in `src/whiteboard-core.js` using the stable ids), local `scenePath`/`previewPath`, `sourceHash`, and bounded stats; poll guidance tells the agent to read the summary first and update the Mermaid source, never the scene file.
The Mermaid source in the artifact stays authoritative; there is no scene-to-Mermaid reverse conversion.

### Telemetry

`src/telemetry.js` posts anonymous events to an Umami endpoint.
The website ID and host can be baked into the bundle at build time via `LAVISH_AXI_UMAMI_HOST`/`LAVISH_AXI_UMAMI_WEBSITE_ID` env vars (consumed by `scripts/build.js` and inlined as `process.env.LAVISH_AXI_BUILD_UMAMI_*` defines).
The build also inlines `package.json`'s version as `process.env.LAVISH_AXI_BUILD_VERSION` for the CLI/server version handshake, with source runs falling back to reading `package.json`.
Users opt out with `LAVISH_AXI_TELEMETRY=0`.
The client is best-effort and must never affect CLI behavior - all errors are swallowed.
No need to explicitly document the telemetry behaviors.

## Things to know when editing

- `run()` short-circuits `--version`/`-v`/`-V` (`isVersionOnlyArgv`) before `ensureStateDir` and `initDefaultTelemetry`, because agent harnesses probe every tool's version at session start and the telemetry drain in the `finally` block costs up to a full second. Any new startup work must go after that short-circuit; `test/cli-version.test.js` guards both the latency budget and the "no telemetry request, no state dir" property.
- `canonicalFile` runs `realpath`, so symlinks resolve to their target before becoming session keys. Two paths that refer to the same file always collapse to one session.
- The SDK injected into artifacts lives in `src/artifact-sdk.js` and is wrapped by `createSdkJs`.
  It executes inside an iframe sandboxed with `allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox allow-downloads` (no `allow-same-origin`), so it cannot read the chrome's DOM - communication is `postMessage` only - and it runs the layout audit in the iframe because the chrome cannot directly inspect the sandboxed document. `allow-popups-to-escape-sandbox` lets popups render as top-level tabs without weakening the artifact iframe. Every `/artifact/*` response also carries the matching CSP `sandbox` policy, so an escaped popup that navigates to an artifact-owned active document remains opaque-origin and cannot become a same-origin application client.
  Nothing (Tailwind, DaisyUI, Mermaid, layout safety CSS) is auto-injected into artifacts; agents choose a design direction via the single-sourced `DESIGN_PRIORITY_RULE` (see AXI integration above).
  The `lavish-axi design` Mermaid snippet chooses dark or light rendering from the effective artifact page background and re-renders when a page-theme or OS appearance change alters that appearance, so do not hardcode one Mermaid theme.
- For rendered Mermaid SVGs outside `.mermaid` containers, the injected SDK still enhances them live: explore mode gives each Mermaid `<svg>` dependency-free viewBox pan (drag) and zoom (wheel), and annotation mode freezes that pan/zoom so a click resolves cleanly to one node instead of panning. It enhances on load and `DOMContentLoaded` and re-runs through a throttled `MutationObserver` because Mermaid renders asynchronously and can re-render. Enhancement touches only the live SVG's `viewBox` and listeners, never the saved artifact, so the diagram still renders identically when opened directly. Node detection, label extraction, and target validation live in `src/mermaid-node.js` so they are unit-testable and shared with the server.
- The whiteboard has six easy-to-reintroduce failure modes, all covered by tests or explained in comments:
  - Mermaid skeletons must be materialized again after Excalidraw's scene fonts load; the first synchronous materialization uses a narrower browser-serif fallback and stores text bounds that clip the eventual Excalifont glyphs.
    Keep the font-load and second-conversion ordering in `convertExcalidrawSkeletonsAfterFontsLoad`, and keep the versioned saved-scene repair expansion-only so it never overwrites user geometry or content.
    The real-browser regression in `test/whiteboard-render.browser.test.js` covers both paths.
  - Mermaid node labels use `<br>` / `<br/>` and a two-character `\n` as line breaks. `parseMermaidToExcalidraw` copies `vertex.text` onto skeleton `label.text` unchanged, so those markers stay literal characters and Excalidraw concatenates "classify<br>checks" into one line. `restoreMermaidLabelLineBreaks` in `src/whiteboard-core.js` must run on skeletons before `convertToExcalidrawElements` (and again on materialized text with a measure pass) so Excalidraw `text` / `originalText` get real `\n` and the box sizes to the line set. When that pass grows a node-label container (rectangle, ellipse, diamond) from the center, it must also reposition the independently stored bound-text `x`/`y` into the new box; skip labelled arrows, whose labels sit at path midpoints. `convertSource` mounts without `restore()`, so Excalidraw will not re-derive that geometry on first paint. `test/whiteboard-core.test.js` and the clipping browser fixture cover both break forms, the fusion case, bound-text recentering, and labelled-arrow skip.
  - The converter breaks with mermaid >= 11.14.0: its parsers reach into mermaid's rendered DOM/db internals, and newer versions silently degrade class/ER/state diagrams and subgraph flowcharts to image fallbacks. `mermaid` is pinned EXACTLY (independent of the artifact-facing Mermaid CDN version in `src/design-reference.js`), and `test/whiteboard-pins.test.js` fails any unpinning; bumping requires a live re-probe of native conversion.
  - Excalidraw's theme must be passed only through the `<Excalidraw theme>` prop, and persisted `appState` must never carry `theme` or a dark-space `viewBackgroundColor`: dark mode renders through an invert filter, so a dark background value or a second theme application double-inverts into a washed-out canvas (`src/whiteboard-core.js` strips both at the persistence boundary).
  - `/whiteboard-assets/*` must keep `Access-Control-Allow-Origin: *` (the opaque-origin frame's font fetches are CORS-gated), `Cache-Control: no-cache` (an unversioned bundle URL plus memory cache serves stale editors after upgrades), and `dotfiles: "allow"` in sendFile (a checkout under a dot-directory otherwise 403s every asset).
  - A sidecar's presence is not a user edit: `startFromConversion` autosaves on view, including scroll/zoom from fit-to-content. `handleInit` must go through `resolveWhiteboardInitAction` so a Mermaid-source change silently re-converts an unmodified-since-conversion scene and only prompts when `savedSceneHasPreservableEdits` finds preservable edits. Treating "saved scene exists with a different hash" as the prompt condition brings back the phantom re-convert/keep banner on live agent updates.
- Any helper `createArtifactSdk` calls must reach the browser through `serializeModuleHelpers` in `createSdkJs`, which turns every export of a shared module (`src/mermaid-node.js`, `src/table-cell.js`) into a same-scope `const`. A module-private function called from the SDK closure compiles fine and only `ReferenceError`s on the first click, so put new helpers in one of those wholesale-serialized modules and export them; a helper may then reference only its own arguments, browser globals, or its sibling exports - never a module-level constant, which is not serialized. Those modules must export functions and nothing else: only functions survive `toString()`, so `serializeModuleHelpers` throws on any other export rather than shipping a `Set` or `RegExp` that would arrive as an empty `{}`. `test/artifact-sdk-bundle.test.js` boots the served bundle and drives a real click, which is what catches an unreachable helper; the module-level unit tests cannot.
- Table-cell annotations attach `src/table-cell.js`'s semantic row/column names as `target` only. The clicked element's own `selector`, `tag`, and `text` keep describing that element, because the on-screen highlight outlines exactly what was clicked. Both coordinates stay silent rather than name a row or column they cannot prove, because a confidently wrong name reads as authoritative and is worse than none: a rowspan is clipped to its own row group, so only one starting in an earlier row of that group (including `rowspan="0"`, which runs to the end of it) makes a row's DOM order stop being its rendered order, and that suppresses the row's positional heading - only a declared `scope="row"` heading survives it - while the column label needs the header row unshifted the same way, plus a row whose colspans sum to the header's and a cell that does not straddle a grouped header.
  A grouped header's `<th rowspan="2">` therefore costs the leaf header row its names and leaves every `<tbody>` row nameable.
  Spans come from the browser-parsed `rowSpan`/`colSpan` whenever present, because HTML's integer rules stop at the first non-digit and render `rowspan="2x"` as a real two-row span that `Number` reads as `NaN`. Resolving a cell walks its whole table, so `context()` computes the target only under `{ table: true }`, which the annotation card passes and `snapshot()` - which calls `context()` for every element in the document - deliberately does not.
- Annotation handlers ignore native controls (`button`, `input`, `select`, `textarea`, `option`, `label`, `summary`, and editable regions) and their descendants, so they stay interactive without markup; `data-lavish-action` opts custom non-native controls out of annotation and gives them a pointer cursor. Artifact-author guidance for input patterns (`data-lavish-question`, `queueKey`, per-question submits) is owned by the input playbook in `src/playbooks.js`.
- For text annotations, `prompt.selector` is the common ancestor/container selector, not the complete identity. Use the `target` range boundaries and snapshot context to locate the exact selected text.
- For Mermaid diagram nodes, a click annotates the whole rendered `<g>` node - not the sub-shape under the cursor - and hover highlights the same node. `SessionStore.normalizeTarget` routes these targets through `normalizeMermaidNodeTarget`, which strips them to the fixed `type`/`diagramId`/`nodeId`/`label`/`selector` shape, while text-range and other/legacy targets pass through unchanged.
- `SessionStore` re-reads and re-writes the entire `state.json` on every operation - there is no in-memory cache. The single server process is necessary but NOT sufficient for consistency: a method that reads state, `await`s, then writes can still interleave with another method's read-modify-write and lose its update. Every mutation therefore serializes through the store's single `AsyncMutex` (`store.lock`, `src/async-mutex.js`) via `runExclusive`; see the Image attachments section for the one lock-free exception (`referencedAttachmentIds`).
- The chrome and the sandboxed artifact document cannot see each other's keyboard events (no `allow-same-origin`), so any keyboard shortcut that must work regardless of focus needs its own capture-phase `document.addEventListener("keydown", ..., true)` in _both_ `src/chrome-client.js` and `src/artifact-sdk.js`, not just one.
  The annotate/explore mode toggle hotkey (`MODE_TOGGLE_HOTKEY_KEY`, Cmd/Ctrl+I) is the reference implementation: the chrome owns the mode state and toggles it directly; the SDK side has no mode state of its own, so on catching the hotkey it `postMessage`s `{ type: "lavish:toggleAnnotationMode" }` to the chrome, which drives the exact same `toggleAnnotationMode()` function the on-screen switch's `onclick` calls.
  Requiring a modifier (`metaKey || ctrlKey`) is what lets the listener safely call `preventDefault()` without breaking plain typing (including typing the bound letter itself) in the chat box or an annotation-card textarea.
- Tests use `LAVISH_AXI_STATE_DIR` and ephemeral ports to stay isolated. When adding tests that spin up the server, do the same.
- **The unit suite structurally cannot catch a dead chrome script.** `test/chrome-client-queue.test.js` runs `src/chrome-client.js` under a `vm` harness whose `getElementById` lazily fabricates any element it asks for, so a null dereference is impossible in there: one stale top-level id keeps the entire suite green while killing the chrome in every artifact (see the crash surface under Hosted sharing). `test/chrome-load-browser.test.js` is the only guard that can see it. It loads a real served session in headless Chrome over raw CDP and asserts the module reached its last statement, every handler attached, and - the load-bearing check - that the ids the served `chrome-client.js` requests are a subset of the ids in the served chrome markup, computed from the served bytes on both sides. Its second test is a negative control that injects one stale lookup into a synthetic copy of the client and requires the probe to report the `TypeError`; a guard that passes both ways would be worse than none. It is opt-in, so a green `pnpm test` is no evidence at all about this failure mode - run it after any change to the chrome markup or client. Do not delete it as redundant with the queue harness.
- Circular close buttons (`.queued-remove`; upstream also names `.share-close`, whose CSS this fork deleted with the share dialog) render an inline SVG x mark with two symmetric strokes, not a text `x`/`&times;` glyph.
  Font metrics put text glyphs off from the geometric center even under flex centering, while the SVG centers via flex plus equal viewBox margins.
  Keep the SVG strokes on `currentColor` so existing hover color rules still apply, and follow this pattern for any new circular icon-only button.
- The in-iframe layout audit (`src/artifact-sdk.js`) is severe-only and fails open on uncertainty; its easy-to-reintroduce failure modes are covered by dedicated and browser-level tests:
  - Scroll dimensions and parent overhang are never proof by themselves. `classifySevereTextOverflow` requires rendered text-range fragments from one semantic text boundary to materially cross that boundary, excludes explicit truncation, masks, and standard visually hidden text, and reports vertical loss only when a line's center leaves its box.
  - Diagram surfaces (`.mermaid`, SVG, and `[data-lavish-ui]`) stay outside the general audit so it does not compete with the separate Mermaid diagram-label clipping path.
  - Page overflow requires both a material document delta and meaningful text or required-control bounds beyond the usable viewport, producing one `html` root finding instead of descendant geometry noise.
  - Finite animations settle before sampling, findings associated with still-active finite or infinite motion stay silent without hiding independent stable failures, and `findStableLayoutFindings` requires the same severe root in two samples.
  - Overlap reports only near-total coverage by one opaque static sibling; decorative transparent overlap stays silent. Warning-severity input is filtered again by the chrome and by `normalizeFindings` in `src/layout-warnings.js`.
  - The audit reports its own completeness. A failed run must publish `complete: false` with no findings, never an empty completed pass - an empty completed pass is read as evidence of repair, so the distinction is what keeps a crashed audit from silently resolving real warnings.

- The chrome page ships from `createChromeHtml` with the layout-gate overlay ALREADY covering the artifact area. `CHROME_BOOT_FAILSAFE_JS` is inlined BEFORE the `<script src="/chrome-client.js">` tag (a request that hangs rather than errors blocks parsing, so a failsafe placed after the tag would never be reached), installs the shared gate escape (`window.__lavishLayoutGateEscape`) before the client can fail, and handles the script's `onerror` and boot timeout. The client reuses that escape and cancels only the boot-failure timer by setting `window.__lavishChromeReady` at the very end of the file. Keep the placement, timeout, end-of-file cancellation, ended-session guard, bounded gate hold, and network-independent **Show anyway** path: the escape must work even when the client script or server does not.
- The artifact iframe carries only `data-artifact-src` and is navigated exclusively by `replaceArtifactFrame`, so a chrome whose FIRST begin-load fails has no previous frame to preserve. Recoverable outcomes (a transport failure past `ARTIFACT_LOAD_BEGIN_RETRY_DELAYS_MS`, or a `no-handoff` whose one re-handshake also failed) schedule a fresh attempt through `ARTIFACT_LOAD_RECOVERY_DELAYS_MS` and, once that is exhausted with nothing on screen, surface `setLayoutGateFailure` instead of a silent blank. `superseded` and `out-of-order` must NOT retry: another reviewer or a newer request in this same chrome owns the artifact, and a background retry would fight it. A `superseded` chrome with nothing on screen names itself on the gate overlay with a **Take over here** button instead of holding the spinner.
- Below 860px the conversation panel is a fixed bottom sheet with a persistent dock (the phone block in `src/chrome.css`; README's Reviewing on a phone bullet owns the user-facing behavior), and the chrome's sheet controller in `src/chrome-client.js` owns open/closed intent, `inert` on the hidden half (and on an ended session), focus handoff, gestures, visual-viewport synchronization, and the dock summary. `MOBILE_SHEET_MEDIA` there must match the CSS breakpoint. Four rules are easy to break: desktop stays pixel-identical only because `.panel-head`/`.panel-head-row` are `display: contents` outside the breakpoint (the `h2` must remain a direct flex child of `.panel`); the collapsed state is a `translateY`, never a height change, so the chat keeps its layout and the sheet can follow a drag, which is also why the phone panel carries a shadow hairline instead of a border (a 1px border pushes the docked head past the viewport edge); the sheet is sized from `--vv-top`/`--vv-height`, which `syncVisualViewport` keeps equal to the visual viewport, so the iOS keyboard shrinks it instead of covering the composer (Android gets the same through `interactive-widget=resizes-content` in the viewport meta, and `viewport-fit=cover` is what makes the safe-area insets non-zero); and the `.chat-attachments` rules in the phone block belong to the composer-attachments feature this fork has not taken, so they stay inert until that markup lands.
- The layout-warning inbox's rules are the product contract, not implementation detail - `src/layout-warnings.js` and `test/layout-warnings.test.js` are the authority, and the lifecycle is also restated for users in README and for agents in the poll guidance. Two invariants are easy to break by accident:
  - Nothing may clear a warning except a newer artifact revision plus a **complete** pass at the **same viewport class** that no longer detects it. Not a closed drawer, a checked box, a queued or delivered prompt, an agent reply, a reload in flight, a temporarily absent element, another viewport passing, or a failed diagnostic run.
  - Adding a route or UI action that emits `feedback` for a detection makes the whole feature regress to the auto-repair churn it replaced. Only user actions (`/api/:key/prompts`) and the narrow fatal path may emit it.
